# Query plans for the hot queries (v3)

Every query the API and worker run on a hot path, explained on a production-sized dataset: 1,000 shows, 500,000 seats, 100,000 holds, about 30,000 bookings and 200,000 outbox rows. Generated by `bench/plans.py`, which builds the dataset in the separate `rushline_bench` database:

```bash
uv run python bench/plans.py            # build the dataset, then explain
uv run python bench/plans.py --reuse    # explain only
```

## Summary (2026-11-26, dev machine)

| Query | Index used | Time | Notes |
|---|---|---|---|
| Shows, first page | `shows_starts_at_id_idx` | 0.14 ms | Reads 21 rows and stops |
| Shows, next page (cursor) | `shows_starts_at_id_idx` | 0.10 ms | The `(starts_at, id) > (...)` row comparison seeks straight in |
| Seat map, on a cache miss | `seats_show_id_status_idx` (bitmap) | 2.7 ms | Sorts 500 rows in memory. Fine, since it runs about once a second per show |
| Claim: lock seats | `seats_pkey` | 0.08 ms | `ORDER BY id FOR UPDATE` |
| Release: a hold's seats | `seats_hold_id_idx` | 0.05 ms | Partial index, only seats that have a hold |
| Worker: due expiries | `holds_open_expires_at_idx` | 0.13 ms | Partial index, only open holds |
| Worker: due payments | `holds_one_open_per_user_show` | 0.20 ms | See below |
| Worker: due captures | `bookings_pending_capture_idx` | 0.03 ms | Partial index |
| Worker: unpublished outbox | `outbox_unpublished_idx` | 0.10 ms | Partial index, 50 of 200,000 rows |
| `GET /bookings` (mine) | `bookings_user_id_id_idx` **(added)** | 0.04 ms | Was a full scan at 2.2 ms |

## What changed

- **Added `bookings (user_id, id)`.** `WHERE user_id = ? ORDER BY id DESC LIMIT 100` was a sequential scan of every booking, at 2.2 ms with 30,000 rows and growing with the table. With the index, it's a backward index scan that stops at 100 rows: 0.037 ms.
- **No index for due payments.** I expected `status = 'paying' AND payment_deadline <= now()` to need one. Instead, Postgres reuses the one-open-hold partial unique index, which only contains `active` and `paying` holds (a few hundred rows), and sorts that small set. Adding an index there would only cost write time.
- **No index for the seat map.** A `(show_id, id)` index would skip the 500-row sort, but the query runs at most about once a second per show because of the cache.
